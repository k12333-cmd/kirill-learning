# Промпты, которые реально нужны

> Не «магические заклинания», а рабочие формулировки под конкретные ситуации. Копируй, подставляй своё.
> Общее правило: **чем точнее вход и ожидание, тем полезнее ответ.**

---

## Изучить тему (десктоп-приложение, не Claude Code)

```
Объясни мне <тема> как человеку, который знает <что уже знаю> и не знает ничего сверх этого.
Мне не нужен полный курс — нужно рабочее понимание: зачем это существует, как устроено
в общих чертах, и что я должен уметь с этим делать на практике.
Приведи один конкретный пример из реального кода.
В конце задай мне 3 вопроса на понимание — я отвечу, а ты скажешь, где я не прав.
```

Последняя строка — самое ценное. Проверка себя дешевле, чем обнаружить дыру на созвоне.

## Разобраться в чужом коде

```
Вот файл: <вставить или указать путь>.
Объясни по блокам: что делает каждый, что приходит на вход, что получается на выходе.
Не переписывай код и не предлагай улучшений — только объясни, что тут происходит.
Отдельно назови: откуда берутся данные, что этот код меняет во внешнем мире,
и какое место здесь самое хрупкое.
```

## Понять свою ошибку

```
Я делал: <что>
Ожидал: <что>
Получил: <текст ошибки ЦЕЛИКОМ>
Уже проверил: <что>

Не чини сразу. Сначала объясни, что означает эта ошибка и почему она возникла именно здесь.
Потом предложи, что проверить, чтобы подтвердить причину.
```

Просить «объясни», а не «почини», — главная привычка. «Почини» лечит симптом, «объясни» лечит тебя.

## План перед задачей

```
Задача: <что нужно получить>
Ограничения: <срок, стек, чего делать нельзя>

Опиши план по шагам, каждый шаг — не больше часа работы.
По каждому шагу: что на входе, что на выходе, как я проверю, что он сделан.
Отдельно: что здесь может пойти не так и где я скорее всего застряну.
Кода пока не пиши.
```

Дальше — вычеркни из плана лишнее и напиши почему. Клод почти всегда предлагает больше, чем требует задача.

---

## Получить код, который сможешь защитить

```
Реализуй шаг <N> из плана. Условия:
- максимально простое решение, без абстракций «на будущее»
- без библиотек сверх тех, что уже в requirements.txt, — если нужна новая, сначала объясни зачем
- после кода объясни его построчно
- отдельно скажи, что сломается при <пустом входе / ошибке сети / отсутствии файла>
```

## Проверить сомнительное

```
Ты предложил использовать <функция/параметр/подход>.
Не отвечай по памяти: покажи, откуда это известно — ссылка на официальную документацию
или способ проверить прямо сейчас командой.
Если не уверен, что это существует в текущей версии, — так и скажи.
```

Если в ответ он «извиняется» и меняет решение — значит, придумал. Записывай случай в `learning-log/клод-врёт.md`.

## Написать критерии приёмки

```
Вот описание задачи: <...>
Сформулируй критерии приёмки в формате Дано → Когда → Тогда.
Требования к формулировкам: по каждому критерию посторонний человек должен уметь ответить
«да/нет», не спрашивая автора. Никаких «быстро», «удобно», «корректно» — только проверяемое.
Обязательно 2 граничных случая и 1 защитный.
```

## Ревью перед PR (в Claude Code)

```
Прогони reviewer по моим изменениям в этой ветке.
```

Чинишь всё 🔴 сам. Если не понял находку — спрашиваешь, что именно сломается, и только потом чинишь.

---

## Чего не делать

| Плохо | Почему | Как надо |
|---|---|---|
| «Напиши мне скрипт для X» | получишь код, который не понимаешь и не сможешь чинить | сначала план, потом код по шагам |
| «Не работает, почини» | без входных данных ответ будет угадыванием | что делал / ожидал / получил / проверил |
| «Сделай красиво / нормально» | нет критерия результата — получишь что угодно | сформулируй проверяемое ожидание |
| Вставить ключ или пароль в чат | утечка, отзывать и перевыпускать | через `.env`, в чат — никогда |
| «Ты прав, спасибо» на непроверенное | согласие модели ничего не доказывает | проверь документацией или запуском |
| Одна сессия на весь день | контекст распухает, растёт расход, падает точность | новая задача — новая сессия |
